# Research: Community Discovery Pipeline

Дата: 2026-08-03  
Статус: рабочая база; стратегия discovery уточнена в `risks-and-strategy.md`

## 1. Контекст продукта (Warmr)

В экосистеме Warmr есть два ключевых объекта:

| Роль | Суть |
|------|------|
| **Vendors** | Компании, которые платят за лиды / «подсказки» (intent) |
| **Communities** | Площадки, где живут потенциальные клиенты; боты мониторят ленту |

Типичный цикл:

1. В комьюнити появляется intent-post («нужен бухгалтер во Флориде»).
2. Бот фиксирует пост в БД.
3. Релевантному вендору уходит лид.
4. Вендор и автор intent договариваются → экономическая ценность.

Качество комьюнити напрямую влияет на качество лидов:

- **Низкая ценность:** мелкий чат (например, 10 человек без профессиональной плотности) → почти ноль.
- **Высокая ценность:** платный вход, сильная ниша, платежеспособная аудитория, достаточный размер.

Текущее состояние inventory:

- ~80 000 сообществ «грязных»
- ~20 000 относительно ценных
- **Цель:** порядка **1 000 000 хороших** сообществ

Этот репозиторий — не мониторинг ленты и не матчинг вендоров.  
Это **машина пополнения inventory**: находить, очищать, оценивать и отдавать новые ценные комьюнити в текущую экосистему.

## 2. Что считается «сообществом»

### In-scope (MVP)

- Professional / industry communities с публичной страницей
- Платные membership-клубы и ассоциации
- Площадки на Circle, Mighty Networks, Discord/Slack **с публичным лендингом**
- Отраслевые форумы и networks, где возможны intent-посты B2B/B2C услуг

### Out-of-scope (MVP)

- Обычные корпоративные сайты / SaaS без community
- Новостные медиа и блоги без membership
- Разовые ивенты без постоянного сообщества
- Instagram / LinkedIn groups как primary source (сложный доступ, нестабильный парсинг)
- Полностью закрытые invite-only без публичной карточки

> Instagram и подобные соцсети **не являются** основным объектом этого тула.  
> Тул ищет **discoverable community landing pages / hubs**, которые потом можно завести в мониторинг экосистемы.

## 3. Проблема брифа и ограничение

Нужен поддерживаемый pipeline, который:

1. Генерирует сотни поисковых запросов (гео, ниша, аудитория, тип).
2. Находит кандидатов через search discovery.
3. Парсит публичные страницы сообществ.
4. Дедуплицирует и отсекает мусор.
5. Классифицирует: Join / Apply / Watch / Reject (+ оценка ценности).
6. Выгружает чистые данные.
7. Запускается регулярно, добавляет только новые/изменённые.

**Ключевое ограничение:** не строить решение на прямом массовом скрейпинге Google SERP.  
Discovery — через API / SearXNG; основной парсинг — по сайтам найденных сообществ.

## 4. Research: discovery-слой

### Google Custom Search JSON API

| Параметр | Факт (на 2026) |
|----------|----------------|
| Доступ | Закрыт для **новых** клиентов |
| Free tier | 100 queries / day |
| Paid | $5 / 1 000 queries, hard cap 10 000 / day |
| Sunset | **1 января 2027** |
| Лимит выдачи | max 10 результатов на запрос, max ~100 на query |

**Вывод:** нельзя делать foundation на CSE. Использовать только если у команды уже есть существующий доступ — и то как временный/дополнительный канал.

### SearXNG

- Self-hosted metasearch с HTTP API (`format=json`).
- Не скрейпит Google SERP напрямую в нашем коде: ходит в настроенные search engines через свой инстанс.
- Публичные инстансы часто режут JSON и нестабильны → для продакшена нужен **свой** Docker-инстанс.
- Документация: https://docs.searxng.org/dev/search_api.html  
- GitHub: https://github.com/searxng/searxng

**Вывод:** **основной discovery-канал = self-hosted SearXNG**.

### Альтернативы (позже)

- Коммерческие Search API (SerpAPI, Bing Web Search и т.п.) — как платный backup по качеству/квотам.
- Seed-листы директорий (directories of communities) — отдельный enrichment-канал без search.

## 5. Research: парсинг

| Инструмент | Роль |
|------------|------|
| **Scrapy** | Основной краулер: скорость, concurrency, pipelines, retries, throttling |
| **Playwright** | Точечно для JS-heavy лендингов (Circle, некоторые SPA) |
| **scrapy-playwright** | Гибрид: Scrapy orchestration + browser только где нужно |

Правило стоимости на масштабе:

- 95%+ URL — обычный HTTP через Scrapy
- 5% — Playwright fallback, если экстрактор пустой / страница явно JS

Прямой массовый browser-crawl всех кандидатов до миллиона — слишком дорогой по CPU/RAM.

## 6. Research: хранение и выгрузка

На объёмах 80k → 1M:

- **Google Sheets / Airtable** — удобная витрина для людей, **не** source of truth.
- **Postgres** — primary store: дедуп, incremental updates, индексы, API для экосистемы.

Рекомендация:

1. Пишем в Postgres.
2. Экспортируем срезы (новые / Join+Apply / high value) в Sheets/Airtable по необходимости.
3. Отдаём в экосистему Warmr через DB sync / API / очередь — см. `integration.md`.

## 7. Классификация и ценность

### Операционный статус (из брифа)

| Статус | Смысл |
|--------|--------|
| **Join** | Есть публичная join/signup-ссылка без тяжёлой заявки |
| **Apply** | Application / waitlist / request to join |
| **Watch** | Похоже на комьюнити, данных мало — нужна ручная/отложенная проверка |
| **Reject** | Не комьюнити, мусор, нерелевантно, дубль |

### Продуктовая ценность (для Warmr)

Отдельное поле `value_score` / `value_tier`, чтобы не смешивать «можно вступить» и «стоит мониторить для лидов».

Сигналы высокой ценности (черновик правил):

- платный вход / membership fee
- размер аудитории выше порога (настраивается по платформе)
- чёткая профессиональная ниша + гео (если нужно вендору)
- признаки B2B/professional density
- активный публичный presence (сайт/лендинг не заброшен)

Сигналы низкой ценности:

- очень маленький размер
- нет ниши / тусовочный чат без проф. контекста
- нет способа вступления и нет полезных контактов
- агрегаторы, витрины, SEO-спам

**Ручная проверка в идеале только на `Watch` и borderline value.**

## 8. Оценка воронки (порядка величин)

Чтобы еженедельно получать тысячи уникальных релевантных:

1. Сотни query-шаблонов × гео × ниша.
2. Discovery даёт десятки тысяч URL-кандидатов.
3. После нормализации + дедупа — тысячи доменов.
4. После relevance/value filter — сотни–тысячи accepted.

MVP-KPI разумнее поставить как:

- стабильный weekly run
- рост **valuable** inventory (не просто raw count)
- reject/noise rate под контролем
- доля ручной проверки низкая

Цель «1M хороших» — стратегическая; тул должен быть **масштабируемым**, а не «разовым скриптом на 1k».

## 9. Итоговые решения ресерча

1. Discovery: **не SearXNG-only**. Primary = seeds/directories + **Brave Search API**; SearXNG = overflow/dev; CSE не foundation.
2. Перед масштабом search — **value model на существующих 80k/20k** (и лидах, если есть).
3. Parse: **Scrapy + Playwright fallback**.
4. Storage: **Postgres** primary; Sheets/Airtable — export.
5. Scope: professional communities с публичной страницей; не Instagram-first.
6. Две оси классификации: **access status** (Join/Apply/Watch/Reject) и **value** (для лидов Warmr).
7. Режим: scheduled incremental pipeline, только new/changed в экосистему.
